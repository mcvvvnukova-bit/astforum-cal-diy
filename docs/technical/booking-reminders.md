# Напоминания о демонстрации через SMTP

Реализация для PUB.02.01.03: Cal.diy → Tasker/PostgreSQL → существующий SMTP Stalwart. Модуль добавляет три автоматических напоминания посетителю. Новые зависимости, таблицы, Redis-очередь и сервис рассылок не требуются.

Статус на 29.09.2026: исходный код реализован в ветке `codex/smtp-booking-reminders`. Производственное включение не выполнялось. Письма о получении заявки, подтверждении, отказе и отмене остаются в существующем механизме Cal.diy.

Коммит реализации: `042d518` (`feat: add durable SMTP booking reminders`). Техническое описание опубликовано 30.09.2026 в [разделе «Техническая реализация» PUB.02.01.03](https://docs.astforum.ru/doc/pub020103-pisma-s-podtverzhdeniem-i-napominaniyami-2NHmdEsUFm#h-tehnicheskaya-realizaciya); сохранение проверено после перезагрузки страницы.

## Правила планирования

| Напоминание | Условия |
| --- | --- |
| За 24 часа | Запись создана минимум за 48 часов до начала; встреча подтверждена до срока напоминания |
| За 60 минут | Встреча подтверждена до срока напоминания |
| За 15 минут | Встреча подтверждена до срока напоминания |

Используется статус `ACCEPTED`. Отменённые, отклонённые, ожидающие подтверждения и прежние перенесённые записи исключаются. Получатель — основной контакт из `responses.email`, сопоставленный с участниками; для старых записей без такого ответа используется первый участник. Дополнительным гостям модуль письма не рассылает.

Рабочий процесс раз в 10 секунд вызывает защищённый `POST /api/tasks/cron`. Cron сначала сверяет задания с сохранёнными записями, затем запускает Tasker. Планировщик читает встречи ближайших 49 часов страницами по 200 записей. Новые задания создаются только для будущих сроков.

Подтверждение учитывается при ближайшей сверке: если срок напоминания уже прошёл до первого обнаружения подтверждения, напоминание не создаётся. Это касается и подтверждения непосредственно перед границей срока, и восстановления после простоя.

Для уже созданного задания допустимо начать отправку в интервале от планового момента до 60 секунд после него. Позже задание пропускается. Это технический допуск запуска, а не гарантия времени доставки в почтовый ящик. При остановке worker просроченные напоминания не догоняются.

Время хранится в UTC. В письмах выводятся дата и время `Europe/Moscow`, формат 24 часа, подпись МСК (GMT+3). Темы и тексты трёх напоминаний соответствуют разделу «Шаблоны писем». Адрес отправителя берётся из `EMAIL_FROM`; конфигурация АСТ Форум задаёт `notifications@astforum.ru`.

## Отмена, перенос и защита от дублей

Тип Tasker: `sendBookingReminder`. Версия расписания определяется идентификатором записи, UID, типом встречи, началом и окончанием. Штатный перенос Cal.diy создаёт новый UID.

Для версии и интервала вычисляется SHA-256; он записывается в `Task.referenceUid`. Существующее уникальное ограничение `(referenceUid, type)` не позволяет создать второе задание. Повторная сверка не изменяет завершённое задание.

Перед SMTP обработчик условным обновлением строки атомарно переводит задание из `queued` в `sending`. Только один конкурентный обработчик получает право отправить письмо. Затем он заново читает запись, её статус, время, актуальную ссылку и выключатели отправки. Tasker не применяет к этому обработчику свой общий механизм успешного завершения и повторов.

При отмене, переносе или выключении отправки старые задания получают `skipped`; строки сохраняются для истории и защиты от повторного создания. Удалять их обычной очисткой очереди нельзя. Повторная проверка исключает устаревшую отправку до вызова SMTP. Отмену, произошедшую уже после последней проверки или после принятия письма SMTP, невозможно отозвать этим механизмом.

## Письмо и ссылки

Используется существующий `serverConfig` и Nodemailer с явной SMTP-конфигурацией. Базовый класс штатных писем не применяется: он перехватывает SMTP-ошибки без передачи вызывающему коду.

Ссылка на встречу читается непосредственно перед отправкой: `metadata.videoCallUrl`, затем действующая `BookingReference.meetingUrl`, затем `location`. Допускаются только HTTP/HTTPS. Если подходящей ссылки нет, кнопка открывает страницу записи.

Перенос и отмена используют штатный `LinkBuilder`. «Добавить в календарь» открывает страницу записи с её текущими календарными действиями. Напоминание не создаёт отдельное приглашение ICS. Права доступа и жизненный цикл календарного приглашения остаются ответственностью существующих обработчиков Cal.diy. HTML экранирует пользовательское имя и ссылки.

## Состояния и ошибки

| `payload.state` | Значение |
| --- | --- |
| `queued` | Ожидает срока или разрешённого повтора |
| `sending` | Задание закреплено за обработчиком; результат SMTP ещё не записан |
| `smtp_accepted` | SMTP подтвердил принятие письма для нужного адресата; это не подтверждение доставки |
| `skipped` | Запись изменилась, отправка выключена или срок истёк |
| `failed` | Постоянная ошибка либо исчерпаны разрешённые повторы |
| `unknown` | SMTP мог принять письмо; автоматический повтор запрещён |

Состояние хранится в JSON-поле `Task.payload`. Там нет адреса получателя и ссылки конференции: они читаются из записи перед отправкой. `attempts` сохраняет число попыток; `lastError` содержит безопасный код причины. Для терминального задания `maxAttempts=0` останавливает общий Tasker. `succeededAt` означает завершение обработки для `smtp_accepted`/`skipped`, а не доставку.

При явном временном отказе SMTP 4xx либо достоверной ошибке до передачи письма выполняется до трёх попыток всего. Минимальный интервал повтора — 10 секунд, все повторы ограничены исходным окном 60 секунд. Ответ 5xx завершает задание ошибкой.

Обрыв соединения или тайм-аут без достоверного результата переводит задание в `unknown`. Nodemailer может обозначить обрыв после DATA как `CONN`, поэтому один этот признак не разрешает повтор. Полный SMTP-вызов ограничен 45 секундами. Состояние `sending`, оставшееся после остановки процесса, через 120 секунд также переводится в `unknown`, включая последнюю попытку.

Стабильный `Message-ID` имеет вид `booking-reminder-<referenceUid>@<домен Cal.diy>`. Он нужен для поиска в журнале Stalwart; SMTP не обязан устранять дубли по этому заголовку. При ошибке записи результата после принятия SMTP сохраняется `sending`, затем `unknown`. Повторной отправки вслепую нет.

## Настройки и включение

| Настройка | Значение / назначение |
| --- | --- |
| `BOOKING_REMINDER_EVENT_TYPE_IDS` | Список ID через запятую; пустое значение выключает модуль. Для текущего demo/60min — `3`, после проверки ID на целевом сервере |
| `CRON_SECRET` | Случайный секрет, одинаковый у `web` и `reminder-worker`; отсутствующий или неверный секрет даёт HTTP 401 |
| `EMAIL_SERVER` либо `EMAIL_SERVER_HOST` и параметры SMTP | Существующее подключение. Конфигурация АСТ Форум использует TLS, Stalwart, порт 465 |
| `EMAIL_FROM`, `EMAIL_FROM_NAME` | `notifications@astforum.ru`, `АСТ Форум` |
| `NEXT_PUBLIC_WEBAPP_URL` | `https://cal.astforum.ru` |
| Compose profile `reminders` | Включает отдельный процесс вызова cron из того же образа приложения |

Дополнительно учитываются глобальный выключатель `Feature.slug=emails` (`enabled=true` выключает письма) и `eventType.metadata.disableStandardEmails.all.attendee=true`. Пустой allowlist останавливает новые напоминания и при следующем cron снимает ожидающие задания.

Сначала собрать образ из проверенного коммита. Затем задать настройки в серверном `.env`, сохранив пароль SMTP вне репозитория. Согласовать новый тег образа в основной конфигурации и действующем `web-command.override.yaml`; старый override может закреплять предыдущий образ.

Пример запуска из корня репозитория после подготовки серверных настроек:

```sh
ACTIVE_WEB_OVERRIDE=/absolute/path/to/current/web-command.override.yaml
docker compose --env-file /opt/astforum-cal-diy/.env \
  -f deployment/astforum/compose.yaml -f "$ACTIVE_WEB_OVERRIDE" \
  --profile reminders config --quiet
docker compose --env-file /opt/astforum-cal-diy/.env \
  -f deployment/astforum/compose.yaml -f "$ACTIVE_WEB_OVERRIDE" \
  --profile reminders up -d web reminder-worker
```

Worker доступен только во внутренней сети Compose и не публикует порты. Проверка здоровья веб-сервера, унаследованная от образа, отключена только у worker. Его ошибки HTTP и тайм-ауты пишутся в stdout/stderr. Неверная конфигурация allowlist останавливает текущий вызов cron: исправить настройку перед следующим запуском.

При отключении очистить allowlist и пересоздать `web`; дать cron выполнить сверку. Уже принятое SMTP письмо отключение не отзывает. Миграция БД и откат схемы не нужны.

## Диагностика

Выполнять в административном подключении к БД:

```sql
SELECT id, "referenceUid", "scheduledAt", attempts,
       payload::jsonb->>'bookingId' AS booking_id,
       payload::jsonb->>'minutesBefore' AS minutes_before,
       payload::jsonb->>'state' AS state, "lastError", "succeededAt"
FROM "Task"
WHERE type = 'sendBookingReminder'
ORDER BY "createdAt" DESC
LIMIT 100;
```

При `unknown` найти Message-ID в журнале Stalwart и установить факт принятия. Не удалять задание и не сбрасывать его в `queued`. Устаревшее напоминание не отправляется повторно. При постоянной ошибке проверить контакт и SMTP-конфигурацию; изменение статуса встречи для этого не требуется.

Текущее расширение реализует backend напоминаний. Отображение очереди и ошибки в карточке команды, кнопка ручной повторной отправки подтверждения, отдельная история ручных операций и обработка уведомлений о недоставке пока не добавлены. Они остаются отдельными частями общих требований PUB.02.01.03. Статус доставки до почтового ящика этот модуль не утверждает.

- Модуль: `packages/features/bookings/reminders/` — правила, шаблоны, Prisma-хранилище, обработчик, SMTP и подключение к cron.

Локально пройден 51 тест: границы времени, позднее подтверждение, отмена/перенос, конкурентные обработчики, повторная сверка, выключатели, число попыток, обрыв SMTP после DATA, ошибка БД после принятия письма и резервные ссылки конференции. SMTP-тесты используют настоящий локальный TCP-приёмник с Nodemailer; тесты Prisma — схему в памяти (Prismock). Проверен фактический экспорт POST-маршрута, хотя веб-сервер Next не запускался.

```sh
node .yarn/releases/yarn-4.12.0.cjs vitest run \
  --config packages/features/bookings/reminders/vitest.config.ts
node .yarn/releases/yarn-4.12.0.cjs tsc \
  -p packages/features/bookings/reminders/tsconfig.json

  -f deployment/astforum/compose.yaml --profile reminders config --quiet
```

В новом checkout сначала установить зависимости и сгенерировать Prisma client/enums штатными командами репозитория. При установке с `--mode=skip-build` для Prismock дополнительно нужен `node node_modules/@prisma/client/scripts/postinstall.js`.

Целевая проверка типов модуля, синтаксис worker и Compose прошли. По результатам ревью исправлены отсутствие POST-экспорта, унаследованный web healthcheck у worker и выбор резервной ссылки конференции. Полная сборка образа, конкурентная проверка на настоящем PostgreSQL, запуск контейнеров и производственная доставка не выполнялись. Перед включением проверить их на тестовой записи с согласованным адресатом.
